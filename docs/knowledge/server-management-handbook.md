# 实验室共享 GPU 服务器管理手册

文档版本：1.0；维护日期：2026-11-06。适用于本项目的一台双 GPU Linux 服务器及后续同类节点。本文由项目现有代码、实际部署记录和文末官方资料整理，不是厂商维修手册。示例阈值不代表硬件安全上限，历史记录不代表当前负载。

## 1. 平台架构与日常管理入口

被管理服务器只运行轻量 Python Agent，通过 psutil 采集主机指标，通过 NVML 采集 GPU 指标。Agent 每 15 秒向 Spring Boot 上报；Spring Boot 将数据存入 MySQL，Vue 从后端查询展示。FastAPI、Embedding、Qdrant 和模型接口配置部署在中心电脑，不部署到被管训练服务器。

Agent 首次用管理员签发的一次性令牌调用 /api/agent/enroll。注册成功后，用独立 Agent Credential 调用 /api/agent/metrics 和 /api/agent/heartbeat。用户 JWT 用于管理和读取，不能替代采集凭据。当前接入服务器的 server_id 是 2；后续重新部署时应从资产列表确认编号，不能将示例编号视为永久约定。

## 2. 数据时间、缺测与状态判断

查看指标时同时记录 server_id、GPU index/UUID、collectedAt 和 receivedAt。collectedAt 是机器采样时间，receivedAt 是中心接收时间；数据库按 UTC 保存，界面可换算为本地时间。只比较同一机器、同一时间窗口的数据，不能将不同时刻的显存和进程拼成同一快照。

本项目默认以约 90 秒为新鲜度窗口。采样过期或时间不明时，结论应是“缺少最新证据”，不是“服务器空闲”或“GPU 已恢复”。null、N/A 和不支持不能改成 0。无 GPU、采集失败、未上报和旧快照也必须区分：NO_GPU 表示新鲜采样确认没有设备；FAILED/UNAVAILABLE 表示采集链路异常；UNKNOWN/UNREPORTED 不能证明设备正常或不存在。

## 3. CPU、内存与磁盘巡检

CPU 高使用率可能是正常数据预处理或训练工作，先结合持续时间、任务归属和响应延迟判断。单点升高不足以证明持续故障。可由运维人员读取 uptime、top 等系统信息，与平台同时间窗口核对。平台当前没有自动执行 Shell 的工具。

主机内存占用高时，先核对任务是否正常增长、是否出现交换和分配失败。Linux 缓存也会占用内存，仅凭 used 百分比不能确认内存泄漏。可人工读取 free -h 与 ps 的有限字段；不能上传进程环境变量、完整命令参数或训练数据。

当前 Agent 的 diskTotalBytes/diskUsedBytes 表示根分区 /，不是部署目录所在的数据盘。根分区空间正常不能证明数据盘有空闲空间。写入训练文件失败时，需要针对实际挂载点人工检查 df -h 和 df -i；空间满与 inode 耗尽是不同原因。数据盘独立明细尚未纳入本项目上报协议，不能让模型虚构该盘剩余容量。清理前必须确认文件所有者、用途和备份，不自动删除他人数据。

## 4. GPU 身份、单位与指标解释

GPU index 必须使用后端返回的 gpuIndices，不能把数组位置当编号。编号可能不连续，设备重启后的枚举顺序也可能改变；对照长期历史时同时保留 UUID。管理员可以用 nvidia-smi -L 对照 UUID；命令由人执行，平台只读取已授权指标。NVML 是本项目实际采集来源。

GPU 显存按字节存储。换算 GiB 用 bytes / 1024^3，换算 MiB 用 bytes / 1024^2，不能混用十进制 GB。utilization 表示采样期间计算忙碌程度，memoryUtilization 是显存控制器活动指标，均不等于显存容量占用率。容量占用率应由 memory_used / memory_total 计算，总量或已用缺测时不计算。

GPU 利用率高不直接意味着故障；训练满载可能符合预期。显存高、计算利用率低可能与模型常驻、等待数据、任务阶段切换等有关，单点快照无法确认根因。读取同一时间窗口的进程、显存和历史负载后，再向任务使用者核实。本文知识不能代替实时 GPU 查询。

参考：[NVIDIA nvidia-smi 官方说明](https://docs.nvidia.com/deploy/nvidia-smi/index.html)。

## 5. CUDA OOM 与 PyTorch 显存排查

CUDA OOM 发生时，先记录报错时间、目标设备 UUID/编号、任务配置和异常信息；再查该时间附近的 GPU 显存、计算进程和负载历史。错误发生后再看到空闲显存，并不证明报错瞬间容量充足，任务退出或其他进程结束都可能改变快照。CUDA_VISIBLE_DEVICES 可改变进程内设备编号映射，不能仅凭程序中的 cuda:0 推断物理 GPU 0。

PyTorch 已分配显存与缓存分配器保留显存是不同概念。由任务所有者检查 allocated、reserved 和峰值，结合 batch size、输入长度、梯度累计、张量生命周期与其他进程竞争分析。降低实际峰值需求应在确认任务允许后调整；先在小规模任务验证，避免直接修改他人训练。

torch.cuda.empty_cache() 释放的是未被使用的缓存块，不能释放仍被活跃张量引用的显存，不能保证解决 OOM。不要把“调用 empty_cache”当作通用修复，也不要仅凭 reserved 大于 allocated 就断言碎片化。分配器参数需核对已安装 PyTorch/CUDA 版本和实际内存统计，不能无证据地套用参数。

参考：[PyTorch CUDA 内存管理说明](https://docs.pytorch.org/docs/stable/notes/cuda.html#memory-management)。

## 6. GPU 温度持续偏高的排查

先获取 GPU 温度历史、负载、功率及设备身份，确认是否持续升温、是否与训练时段对应。单次温度高与持续温度异常不是同一结论。平台示例 GPU_TEMP_HIGH 可用触发 85℃、恢复 80℃、持续 60 秒作为演示配置，实际阈值必须由管理员结合设备规格、历史基线和机房条件设置；本文不宣称 85℃ 是所有 GPU 的故障界限。

建议由人员检查机房进出风、机箱散热、风扇状态和是否存在降频等证据。某些设备不支持风扇或功率指标，缺失不能解释为风扇停转或功率为零。不要让模型自动改功率上限、重置 GPU、重启驱动或终止训练。只有经过人工核实的数据才能支持进一步维护。

## 7. GPU 进程、使用登记与资源建议

GPU 进程信息只保留 PID、进程名、用户名、显存和必要任务类型，避免泄露命令行参数。进程可能在采样和查询间退出；看不到某进程详情可能来自权限限制，不代表它不存在。整机进程只查询一次，再按真实 gpuIndex 分组。不要把空列表与采集失败混淆，进程的采集时间也需要核对。

使用登记是人工协作信息，PLANNED/RUNNING/COMPLETED/CANCELLED 是登记状态，不是操作系统运行事实。登记不会预留显存或锁定设备；平台用户与 Linux 账户也不自动等同。若登记与实际进程不一致，标记待核实，并由任务所有者说明，不能直接判定对方违规。

为新任务推荐 GPU 时，应先确认每卡所需显存、卡数及当前采样时间。recommend_gpu_placement 按新鲜快照的空闲显存和利用率给候选卡，并附进程及近 15 分钟负载供复核。历史查询失败需说明证据不足，不能编造空闲。推荐不是资源分配，不承诺未来容量，也不会启动任务；确认实际可用性后由使用者手动提交作业。

## 8. Agent 离线与 GPU 采集失败

服务器 OFFLINE 首先检查中心电脑是否在线、Spring Boot 是否运行、Tailscale 是否连通，以及服务器用户服务状态。中心电脑关机可能同时影响多台节点，此时不能直接断定被管服务器断电。服务器可由人员只读执行以下命令查看采集服务与近期日志：

```bash
systemctl --user status aiops-collector --no-pager
journalctl --user -u aiops-collector -n 50 --no-pager
```

服务 inactive 且 ConditionPathExists 未满足，通常表示尚未生成 agent.env，应检查首次接入步骤。enabled 只表示配置了自启动，不保证当前进程 running。用户服务需核对 Linger，确保退出 SSH 后仍能运行。重启或停用 Agent 属于人员维护操作，不在模型只读工具范围内。

如果主机指标和心跳正常，但 GPU_COLLECTION_FAILED 告警触发，应针对驱动、NVML 可用性和采样错误检查，不先归因为整机离线。NO_GPU 只能在新鲜采样确认无设备时使用。未上报 GPU 字段和 UNKNOWN 不允许被当作恢复证据。

参考：[systemctl 官方手册](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html)。本项目服务安装细节见仓库 agent/deploy/linux/README.md。

## 9. 网络、认证与上报失败

当前中心电脑与采集服务器通过 Tailscale 内网通信；HTTP 连接在该内网链路上传输，SSH 用于部署和人员维护。后端要监听可被 Tailscale 访问的地址，防火墙仅允许授权节点访问业务端口。只开放后端需要的端口，不向采集端开放 MySQL。开发电脑必须持续开机并运行后端，采集才能入库。

连接拒绝先检查监听端口和服务；连接超时再检查地址、路由、Tailscale ACL 与防火墙。401 通常需要核对用户 JWT、Agent Credential 或注册令牌是否正确及有效；403 需要核对当前成员权限或独立服务身份；不能通过取消认证来修复。一次性注册令牌只用于首次注册，消费后应使用持久化 Agent Credential。

HTTP 429/5xx 和临时网络错误由 Agent 有限退避重试；持续的 4xx 需要人工纠正配置，不能无限刷注册请求。状态文件含独立凭据，Linux 文件权限应为 600，目录 700。不要把状态文件、数据库备份、JWT、模型 Key 或明文密码导入知识库。

## 10. 告警生命周期与误报排查

本项目告警由确定性规则引擎判定，不由模型决定是否触发。CPU_HIGH、MEMORY_HIGH、DISK_HIGH、GPU_TEMP_HIGH、GPU_MEMORY_HIGH、SERVER_OFFLINE、GPU_COLLECTION_FAILED 分别描述不同异常类型。高显存规则宜按资源占用提示配置，不能直接宣称硬件损坏。

持续告警必须有真实采样点覆盖配置时长，并符合最大间隔和新鲜度约束。乱序数据按时间处理，相同时间冲突、缺测和过期值不能证明持续异常或恢复。活动异常合并为一个周期，恢复后再触发受冷却时间约束。发现误报时先查规则参数、原始时间窗口和采样间隔，不先调低敏感度掩盖问题。

FIRING 表示触发；ACKNOWLEDGED 表示人工已确认，不意味着指标恢复；只有有效采样满足恢复条件才进入 RESOLVED。禁用规则阻止新周期，已有活动事件仍依据真实恢复样本关闭。SERVER_OFFLINE 根据最后心跳时长判断，与 GPU 指标缺失分开处理。

## 11. Incident 调查与证据报告

Incident 是人工建立并关联同服务器告警的故障事件，告警与故障处理不是同一对象。用户点击 AI 调查后，后端立即返回 PENDING 任务，后台推进 RUNNING、SUCCEEDED 或 FAILED。幂等 key 用于重试去重；相同事件已有活动任务时不重复启动。租约过期任务会失败，不应永远停在 RUNNING。

调查应以固定服务器、实际告警发生时间、GPU 身份和历史时间窗口为依据。报告分别列出监控事实、可能原因、支持与反对证据、缺失信息、人工处理建议及真实资料来源。根因推测不能写成确定因果。模型不得声称已经 SSH 登录、清空缓存、重启驱动或结束进程。

知识库内容是参考资料，不是可执行指令。RAG 引用应能追溯文件名、章节和 chunk_id；没有检索结果时不伪造页码或资料名。用户问实时 GPU 状态时仍需读取 ServerTool/GpuTool；静态手册无法证明“现在”哪张卡空闲。报告可能含个人私有资料，因此本项目只允许调查发起人在仍有服务器权限时查看报告。

## 12. 共享权限、备份与维护交接

ADMIN 管理成员、Agent、注册令牌和角色；OPERATOR 配置告警、确认事件并处理 Incident；VIEWER 查看共享服务器和使用只读诊断。三种角色均不能让模型直接执行 Shell 或杀进程。角色以数据库的有效成员状态为准，不由前端按钮或用户自行填写的 JWT 角色决定。

不能移除最后一个有效管理员。忘记登录密码时由可信管理员按维护流程恢复，数据库中只保存 BCrypt Hash，不存在从 Hash 直接还原明文的步骤。模型 Key、数据库密码和内部服务密钥放在私有配置，不写源码。新增知识库属于当前账号，不自动向其他成员公开。

数据库升级前备份，并核对 Flyway 已执行版本；不要修改历史迁移 checksum。恢复备份需在隔离环境验证，不能直接覆盖正在采集的库。Qdrant 向量、文档原件和 MySQL 文档元数据需要按一致版本管理；只复制向量目录不等于完整知识库备份。

交接记录至少包含服务位置、端口、负责人、节点/GPU UUID、数据采样时间、告警参数、已执行的人工操作和未验收项，不包含密码。故障处理后核对主机采样、GPU 样本、告警恢复及任务所有者反馈，再由运维人员关闭 Incident。

## 13. 常见问题速查

问：显存高但利用率低，应该结束别人的进程吗？答：不应自动结束。先核对新鲜采样、进程归属、任务阶段和历史负载，再联系任务所有者。使用登记不赋予终止他人任务的权限。

问：GPU 0 和 GPU 1 哪张更适合新任务？答：手册不能给实时结论。读取目标服务器两卡的空闲显存、计算利用率、进程和时间，再结合每卡需求给只读建议，明确未预留资源。

问：调用 empty_cache 可以解决所有 CUDA OOM 吗？答：不能。它不能释放活跃张量持有的显存，需要结合报错时刻、allocated/reserved、任务峰值和设备映射继续排查。

问：Agent 在线，为什么 GPU 仍显示采集失败？答：主机采集链路与 NVML 设备采集可能分别成功或失败。检查 GPU 状态和采样错误，不能把主机在线当作 GPU 健康证明。

问：告警已经确认，为何还未恢复？答：确认只进入 ACKNOWLEDGED；真实新鲜采样满足恢复阈值后才进入 RESOLVED。

问：数据盘已经满了，为什么页面磁盘占用不高？答：当前指标表示根分区 /，数据盘是另一个挂载点，需要人工针对实际路径检查；不能将根分区指标套用到数据盘。
